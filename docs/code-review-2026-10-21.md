# รีวิวโค้ดก่อนเพิ่มระบบย้ายสตูดิโอ

ตรวจวันที่ 21 ตุลาคม 2026 จาก RTF ทั้งสี่ไฟล์ที่ผู้ใช้ส่งมา โดยแปลงด้วย Pandoc เป็น UTF-8 ใน `apps-script/` ไม่มีการแก้พฤติกรรมของแอปในชุด import นี้

**ผลประเมิน: ใช้เป็นฐานพัฒนาต่อได้ แต่ยังไม่ควรใช้เป็นยอดยืนยันการย้ายจริงจนแก้ปัญหาข้อมูลและการบันทึกด้านล่าง**

โครงสร้างที่ใช้ต่อได้: Equipment ID สำหรับชนิดอุปกรณ์, Unit ID รายชิ้น, soft delete, การตรวจ S/N ซ้ำในหน้าแก้รายชิ้น, Productions / ProductionChecklist, script lock ในหลายจุด และการเขียน checkbox แบบกลุ่ม

## ปัญหาที่มีกรณีทดสอบยืนยัน

เลขบรรทัดอ้างอิงไฟล์ UTF-8 ใน PR ชุด import นี้ ไม่ใช่บรรทัดของไฟล์ RTF

| รหัส | ระดับ | จุดในโค้ด | เหตุการณ์และผลกระทบ | แนวทางแก้ก่อนใช้งานย้าย |
|---|---|---|---|---|
| R1 | สูง | `apps-script/code.gs:734–771`, เรียกจาก refresh ที่ 782 | มีอุปกรณ์ใช้งานได้ 2 ชิ้น เปลี่ยนยอดใน master เป็นใช้งานได้ 1 + ส่งซ่อม 1 แล้ว sync: ระบบสร้าง Unit ใหม่เพิ่มเป็น 3 ชิ้น เพราะเติมจำนวนที่ขาดแยกตามสถานะ แต่ไม่ลดสถานะเดิม | ให้ Unit เป็นข้อมูลจริง; master เป็นยอดสรุป หรือใช้หน้าปรับยอดที่แสดง diff และให้ระบุ Unit ที่เปลี่ยนสถานะ ห้ามอนุมานว่าเป็นของใหม่จากส่วนต่างสถานะ |
| R2 | สูง | `apps-script/code.gs:814–822` | Unit แรกไม่มี S/N และ Unit ที่สองมี SN-B; master เก็บเฉพาะ SN-B; refresh จับ serial ตามลำดับแถว ทำให้ SN-B ย้ายไป Unit แรก และล้างจาก Unit ที่สอง | รักษาการผูก S/N กับ Unit ID; การ import ต้องจับคู่ด้วย ID และแสดงข้อขัดแย้ง ห้ามใช้ตำแหน่งแถวเป็นตัวระบุชิ้น |
| R3 | กลาง | `apps-script/code.gs:274–281` | ส่ง serial ใหม่พร้อม status ที่ไม่ถูกต้อง: serial ถูกเขียนก่อน จากนั้นคำสั่งจึงโยน error ผู้ใช้เห็นว่าบันทึกไม่สำเร็จแต่ข้อมูลบางส่วนเปลี่ยนแล้ว | validate ทุก field ก่อนเริ่มเขียน และออกแบบการเขียนให้ตรวจผล/ลองซ้ำได้ |
| R4 | สูงเมื่อใช้หลายคน | `apps-script/code.gs:618–630`, `1083–1094` | `closeProduction` ตรวจยอดและปิดกองโดยไม่มี lock ร่วมกัน; อีกคำขออาจเพิ่มของหรือยกเลิกการรับกลับระหว่างสองขั้นตอน ทำให้ปิดกองพร้อมยอดค้าง | ล็อกตั้งแต่ตรวจข้อมูลจนเปลี่ยนสถานะ; `addProductionUnits` ต้องตรวจสถานะกองซ้ำภายใน lock ด้วย |
| R5 | สูง | `apps-script/app.html:713–749` | ระหว่างบันทึกชุดแรก ผู้ใช้ติ๊กรายการเพิ่ม แล้วการบันทึกชุดแรกผิดพลาด: catch ล้าง pending ทั้งหมด รวมการติ๊กที่ยังไม่เคยส่ง | เก็บคิวแยกตาม Job ID, เก็บ edits ที่ยังไม่ยืนยัน, มี retry/reconcile และห้ามขึ้นว่าบันทึกแล้วจนได้รับผลยืนยัน |
| R6 | สูง | `apps-script/index.html:254`, `apps-script/code.gs:46` | ค่า `job` จาก URL ถูกส่งเข้า `<script>` ด้วย force-print + JSON.stringify; ค่า `</script>` สามารถปิด script เดิมและแทรก HTML ได้ | จำกัดรูปแบบ Job ID และ serialize ค่าใน script อย่างปลอดภัย เช่น escape `<` เป็น `\u003c`; ตรวจทั้งกรณี URL และ config |
| R7 | สูง | `apps-script/app.html:1225–1230` | ชื่อหมวดหมู่จากข้อมูลถูกใส่ `innerHTML` โดยตรง จึงสร้างแท็ก HTML ได้เมื่อข้อมูลมี markup | สร้าง element แล้วใส่ชื่อผ่าน `textContent`; เก็บ innerHTML สำหรับส่วนโครงสร้างที่ไม่มีข้อความจากผู้ใช้ |

R1–R5 ทดสอบด้วย VM และบริการ Sheet/lock จำลอง; R6–R7 ทดสอบยืนยันว่า source สร้าง HTML ที่ไม่ปลอดภัย ไม่ได้รัน payload บนระบบบริษัทหรือยืนยันการโจมตี live

## ประเด็นที่ตรวจพบจากโค้ดและต้องจัดการเพิ่ม

1. **ขอบเขต API และสิทธิ์:** helper ที่เขียนข้อมูล เช่น `setProductionStatus` เป็น global function ไม่ลงท้าย `_` และไม่ตรวจสิทธิ์ จึงเป็นจุดเรียกผ่าน `google.script.run` ที่ข้ามข้อกำหนดของ `closeProduction` ได้สำหรับผู้ที่เข้าถึงเว็บ ควรทำ helper เป็น private และตรวจผู้มีสิทธิ์ใน public mutation ทุกจุด ไม่มี deployment settings / manifest แนบมา จึงยังบอกไม่ได้ว่าใครเข้าถึงเว็บจริงได้บ้าง
2. **การรวมการ์ด:** `groupKey` ใน `app.html:153` ใช้ชื่อกับสถานะ ไม่ใช้ Equipment ID ทำให้ชนิดอุปกรณ์ต่าง ID ที่ชื่อเหมือนกันรวมกันได้ แล้วเมนูแก้กลุ่มไปกระทบหลายชนิด ควรใช้ Equipment ID สำหรับการรวมและแก้ไข
3. **ประวัติและสถานะรายชิ้น:** `getProduction` เขียนทับข้อมูลที่แสดงจาก snapshot ด้วยค่าปัจจุบัน (`code.gs:374–381`) จึงใช้เป็นหลักฐานสภาพก่อนย้ายไม่ได้โดยตรง; `deleteUnits` ยังไม่ตรวจว่าชิ้นนั้นติดกองหรือรอตรวจรับอยู่ ควรมีประวัติแยกและข้อกำหนดการนำออกจากคลัง

## สิ่งที่ยังไม่มีสำหรับงานย้าย

ยังไม่มีรอบย้าย / รหัสกล่อง / สถานที่จริงของแต่ละชิ้น / รูปอุปกรณ์ / รูปก่อน–หลังย้าย / ผลตรวจรับพร้อมผู้ตรวจ / ประวัติการรับเข้า / มุมมองคลังออฟฟิศใหม่ การมีฟิลด์ Location เดิมอย่างเดียวไม่พอ เพราะยังปะปนระหว่างที่เก็บและสถานะการขนส่ง

## ผลทดสอบ

- `npm run check`: ผ่าน JavaScript syntax ทั้งฝั่ง server/client, DOM ID ที่เรียกใช้งาน, include และชื่อ API ที่หน้าเว็บเรียก
- `npm run test:readiness`: **ไม่ผ่าน 7/7 กรณี** ตามปัญหาที่ระบุ เป็นเทสต์เงื่อนไขที่ควรเป็น ไม่ได้เขียนให้ยอมรับพฤติกรรมผิด เทสต์ควรผ่านหลังแก้แต่ละข้อ
- ไม่ได้เชื่อม Google Sheet จริง ไม่ได้เรียก setupSystem / repair / refresh บนระบบจริง และยังไม่ได้ deploy Apps Script
- ไม่ได้รับ manifest, trigger configuration, deployed version หรือ Drive permission จึงยังไม่ตรวจสิทธิ์และ runtime แบบครบระบบ

## ลำดับทำต่อ

1. สำรอง Google Sheet ปัจจุบันและสรุปยอด active Unit / S/N ซ้ำ / ID ซ้ำ / ยอด master ต่างจาก Unit โดยอ่านอย่างเดียว
2. แก้ R1–R2 และกำหนด Unit เป็นข้อมูลหลัก; import แบบ preview ก่อนเขียน
3. แก้ R3–R7, helper API และการรวมการ์ด; ทดสอบการบันทึกพร้อมกัน/สัญญาณขาด
4. เพิ่มรอบย้ายและรูป พร้อม snapshot ของข้อมูลตอนส่งออกและตอนรับเข้า
5. ใช้การยืนยันรับเข้าปรับตำแหน่งปัจจุบันของ Unit เดิม แล้วให้คลังใหม่กรองเฉพาะที่รับถึงแล้ว
6. ทดลองกับข้อมูลสำเนาและกล่องตัวอย่าง ก่อนใช้เป็นรายการส่งมอบจริง
